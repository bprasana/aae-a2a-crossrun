# Findings: AAE for A2A cross-run, independent receiver

## Scope of this review

This is a bounded independent run of the published cross-run cases for the AAE extension for A2A v1, at commit 6c857eeb60a9dac379954f5be5900a10616dfc7b of MoltyCel/aae-a2a-extension. An independent receiver was built from the profile text and run against the thirteen cases in the offline form described in run-report.md. The run establishes what run-report.md states and nothing more. It is not a conformance result for the profile, for AAE -02 or for A2A, and it is not an endorsement of any implementation.

One limit applies to everything here. The run was not blind. The expected results are published in the cases file and in the guide, and the implementer had read them. The run shows the expectations are reachable by a second party working from the text. It cannot show the expectations are the right ones. The answers below separate those two claims.

## What the run answers directly

The question Lars Kroehl put to this run was whether an independent receiver can keep apart the two records the paired cases produce, from the record alone. It can. An accepted request whose skill then fails leaves a record that says ACCEPT, steps 1 to 7, the digest of the request that was decided on, and a task that failed in the skill. A request rejected at the mandate check leaves a record that says REJECT, the step, the reason, the same form of digest, and a skill that was never invoked. Section 8.3's rule, that the receipt stands whatever terminal state the task reaches, is what makes the first record readable, and this run's receiver read both records without confusing them and without inferring anything either record did not carry.

The digest mechanism holds up under independent implementation. A JCS canonicalizer written from RFC 8785 reproduced the published vectors octet for octet and then matched all eleven digests in the case set, including the case built to break naive hashing: members out of order, an integral value sent as 120.0, a fraction and a non-ASCII string. A receiver that holds the request can recompute the digest and check a receipt against it. That is the property an auditor needs, and it survives a second implementation.

The step and reason vocabulary is precise enough to agree on. This receiver matched not only the guide's pass criteria but the expected step and the expected reason code on all six rejections. Two of those rejections, the forged envelope at step 1 and the wrongly signed challenge response at step 4, were decided by Ed25519 verification against the published DID documents, after the verification code itself had been checked against those documents. The negative cases are the strong part of the set: each refuses at the first check that fails and reports that check.

## Gaps and ambiguities, tied to cases

- XR-G1, all cases. The run is not blind, and the case set cannot make it blind. The expected results ship inside cases.json and in the guide's table. An implementer can keep his code from reading them, as this run did, but he cannot unread them himself. A future round that wants blindness has to withhold the expectations from the implementer, the way a sealed round does.
- XR-G2, all cases. The guide's reporting form does not fit an offline receiver run. Guide Section 6 requires a result file naming both implementations by commit and the server by its Agent Card, which presumes the interactive run of guide Section 5. The offline form, which the editor proposed for this run and which this run used, has no live counterpart and no commits to name. This run reports in its own results.json and states the mapping in run-report.md. If offline receiver runs are a form the editor wants to keep, the guide needs a reporting shape for them.
- XR-G3, XR-01 to XR-11. The audience is not fixed by the inputs. Guide Section 3 builds allowed_domains from the host of params.audience, and XR-11 turns on the comparison, but neither cases.json nor the guide fixes an audience value for the run. This run used the audience of the spec's own Section 4 example. The XR-11 outcome is stable under any choice, since the variant names a foreign domain, but the positive domain every other case relies on is the run's choice, not a published value.
- XR-G4, XR-01 to XR-11. The nonce form is fixed by reference to -02 Section 5 step 4 and is not reproduced in the profile. A receiver built from the profile alone cannot know the form, and cannot verify a nonce another server minted. This run's receiver mints nonces with an HMAC authenticator under its own test secret and verifies only its own, which is all Section 7.3 requires for its own tasks. Challenge interop between independent implementations on the nonce format is untested by this case set.
- XR-G5, step 4 generally. The profile names an iat window for the challenge response and gives no values. This run fixed 300 seconds into the past and 60 into the future. No case exercises either boundary, so the choice is untested in both directions. Two implementations can set different windows and both claim the text; a case at the boundary would force the values into the open.
- XR-G6, step 1 and step 2. The profile puts cty in step 2 but the step 1 signing-authority check needs the payload's issuer, so the payload must be read before its schema step. This run parses leniently for step 1 and strictly, rejecting duplicate member names, at step 2, and reports an unparseable payload at step 2. No case exercises an unparseable payload, so the placement is this run's reading, not a tested agreement.
- XR-G7, XR-12 and XR-13. The two error cases are decided at the protocol layer, before any record of an exchange exists. The receiver's outcome rests on the card's required flag and the shape of the presentation, not on reconstructed evidence. They belong in the set, but they test a different thing from the other eleven, and the guide's pass rule reflects that: the JSON-RPC code decides, and a differing reason code is a note, not a failure.
- XR-G8, XR-06. The case pins that the task id differs from XR-01's and that the digest is the same. It does not pin how task ids or AAE ids are formed. This run derives both deterministically so the run reproduces; a live implementation would mint them fresh. The outcome does not depend on the values, but a reader of two runs cannot tell from the case set whether id formation is expected to be random, sequential or derived.
- XR-G9, coverage. Grant evaluation at step 6 and the delegation chain at step 9 are outside this case set, as guide Section 8 states. This receiver rejects an envelope carrying grants, because spec Section 7.4 requires a server that does not implement -02 Section 2.2.3 to reject, and it does not implement step 9. Neither path is exercised here and this report claims neither. The PENDING grant verdict of -02, a decision deferred to a named authority and closed later by a ratification record, has no case in this set and no reporting form in version 1 of the profile beyond a rejection as grant_pending. For agent systems that defer decisions to people, that is the case that matters most, and it is the case the set does not carry.

## Inventions of this run, named

Per the rule the implementer set on the registry list: where the text is silent, the invention is reported under the implementer's own name.

1. The audience value, taken from the spec's Section 4 example (XR-G3).
2. The nonce construction: a receiver-minted random part, an expiry and an HMAC-SHA256 authenticator under a receiver test secret (XR-G4).
3. The iat window: 300 seconds past, 60 seconds future (XR-G5).
4. An input bound of 65536 bytes per JWS, where spec Section 10.6 leaves the bound to the server.
5. Deterministic VC ids and task ids, derived by uuid5 from the case id, so the run reproduces byte for byte (XR-G8).
6. The frozen evaluation instant, 2026-10-30T20:15:00Z, used for every temporal check and every issued validity window.

## What this run does not establish

It does not establish that the published expectations are the correct expectations for the profile; the expectations and the cases were authored by the same project that wrote the spec. It does not establish conformance of this receiver to the profile, because the interactive run the guide defines was not performed. It does not establish that a second implementation would agree on inputs neither has seen, in particular on the nonce format and the iat window, where the text is silent. It establishes one narrower thing, and establishes it cleanly: the decision record the profile defines, receipt or rejection with the request digest recomputed from the request alone, can be produced and read by an independent party, and the paired records at the centre of the set, an authorized failure and an unauthorized request, cannot be confused with each other from the record alone.
